## 三. 数据库设计

### 3.1 Schema 设计要点

**文件**：`src/db/schema.sql`

**5 张表 + 1 个视图**：

| 表 | 说明 |
|---|---|
| `brands` | 甲方/品牌方 |
| `creators` | 达人档案（核心表） |
| `deals` | 商单记录 |
| `deal_reviews` | 商单复盘 |
| `party_traits` | **【核心】达人/甲方的脾气与注意事项** |
| `v_creator_overview`（视图） | 达人概览聚合 |

### 3.2 核心设计一：两类字段分离

```sql
-- 量化字段 → SQL 硬过滤
followers           INTEGER      -- 粉丝数
female_ratio        NUMERIC(4,3) -- 女性粉丝占比
quote_embed_30s     INTEGER      -- 植入30s报价

-- 文本字段 → 向量语义检索
profile_text        TEXT         -- 达人画像描述
cooperation_history TEXT         -- 历史合作情况【私有资产】
```

**为什么必须分离**：混合检索的基础。语义检索处理不了"粉丝 5-30 万"这类数值条件，必须靠 SQL。

### 3.3 核心设计二：报价双模式

**按业务规则设计**：

```sql
-- 植入：按时长固定档位
quote_embed_15s     INTEGER,
quote_embed_30s     INTEGER,
quote_embed_60s     INTEGER,
-- 定制：整条报价
quote_custom        INTEGER,
-- 两种模式均可做，非二选一
coop_models         TEXT[] DEFAULT '{"placement","custom"}'
```

**约定**：不涉及直播相关字段。

### 3.4 核心设计三：party_traits（私有经验资产）

```sql
CREATE TABLE party_traits (
    trait_id        VARCHAR(16) PRIMARY KEY,
    party_type      VARCHAR(16) NOT NULL,   -- creator / brand
    party_id        VARCHAR(16) NOT NULL,
    trait_category  VARCHAR(32) NOT NULL,   -- 沟通偏好/改稿态度/排期习惯/付款要求/内容尺度
    trait_content   TEXT NOT NULL,
    severity        VARCHAR(16) DEFAULT 'info',  -- info/warning/critical
    source_deal_id  VARCHAR(16),            -- 来源商单
    source_quote    TEXT,                   -- 【防幻觉关键】原始材料原话
    confidence      NUMERIC(3,2),           -- 抽取置信度
    verified        BOOLEAN DEFAULT FALSE   -- 仅 TRUE 参与检索
);
```

**三条硬约束**：
1. `source_quote` 必须保留原文 —— 可溯源、防幻觉
2. `verified = FALSE` 的不参与检索 —— 防脏数据污染
3. 查询时只列条目原文 —— **不做二次生成**（生成会引入幻觉）

### 3.5 索引设计

```sql
CREATE INDEX idx_creators_platform    ON creators(platform);
CREATE INDEX idx_creators_followers   ON creators(followers);
CREATE INDEX idx_creators_category    ON creators(category);
CREATE INDEX idx_creators_female      ON creators(female_ratio);
CREATE INDEX idx_creators_quote_embed ON creators(quote_embed_30s);
CREATE INDEX idx_traits_verified      ON party_traits(verified);
```

**理由**：混合检索的 SQL 过滤层会频繁使用这些条件，索引保证性能。

## 四. 种子数据设计

### 4.1 数据规模

**文件**：`data/seed_data.json`

| 实体 | 数量 | 覆盖 |
|---|---|---|
| 甲方 | 8 | 美妆×2、母婴、食品、3C数码、服饰、宠物、家居 |
| 达人 | 89 | 18 个垂类，抖音/小红书/B站，粉丝 2.9万~8000万（真实昵称，数值估算） |
| 商单 | 17 | 含 settled/producing/signed 各状态 |
| party_traits | 30 | 沟通偏好13、内容尺度10、排期习惯5、付款要求2 |
| 商单复盘 | 18 | agency 14、brand 3、creator 1（仅关联 settled 商单） |

**品牌名为虚构**；达人含真实昵称（粉丝数/报价/占比为估算值），仅用于演示与评测。

### 4.2 专为评测设计的样本

**① 边界样本（检验过滤精度）**

| ID | 昵称 | 粉丝 | 女性占比 | 植入30s | 设计意图 |
|---|---|---|---|---|---|
| C019 | 小鹿の日常 | 29,000 | **0.690** | 1,800 | 卡在 0.70 之下，**应被排除** |
| C003 | 成分党老李 | 245,000 | **0.710** | 20,000 | 卡在 0.70 之上，**应被纳入** |

查询"女性占比 ≥ 0.70"时，这两个样本能立刻暴露过滤逻辑是否正确。

**② 报价分布（覆盖预算查询边界）**

| 垂类 | 植入30s区间 | 定制区间 | 数量 |
|---|---|---|---|
| 3C数码 | 3,600 ~ 32,000 | 6,000 ~ 58,000 | 3 |
| 宠物 | 6,200 ~ 10,800 | 10,500 ~ 19,500 | 2 |
| 服饰 | 10,000 ~ 19,500 | 18,000 ~ 35,000 | 3 |
| 家居 | 4,400 ~ 8,600 | 7,200 ~ 15,000 | 2 |
| 美妆 | 2,800 ~ 20,000 | 4,800 ~ 38,000 | 5 |
| 母婴 | 4,800 ~ 26,000 | 7,500 ~ 48,000 | 2 |
| 食品 | 1,800 ~ 13,000 | 3,200 ~ 24,000 | 3 |

**③ trait 的 severity 分级**

30 条中有 **8 条 critical**，例如：
- `T003` C002：必须提前一周拿到完整brief，临期给脚本会取消
- `T006` C004：必须提供质检报告，有争议成分要求换配方
- `T014` C010：拒绝正文出现促销信息，只接受评论区置顶
- `T026` C018：坚持独立评测结论，需签不干预条款

**这些是"公司私有经验"的具体体现**，也是查询时应优先展示的内容。

**④ source_quote 都保留原话**

例如 T003 的 `source_quote`：
> "不要在拍摄前一夜给新脚本，否则她会直接取消"

**不是 LLM 的总结，是原始材料的引用。** 这是防幻觉的基础。

### 4.3 商单复盘数据（deal_reviews，2026-09-21 补充）

`deal_reviews` 表初版 0 行，为满足步骤 ③ 向量化需求，补充 18 条复盘种子数据：

| 维度 | 分布 |
|---|---|
| reviewer_role | agency 14 / brand 3 / creator 1 |
| rating | 5 分×5 / 4 分×10 / 3 分×3 |
| 关联商单 | 仅关联 `status = settled` 的部分商单 |

**设计约定**：
- 复盘**只写给已结算（settled）的商单**，未完成的单不写复盘。

## 六. 环境问题排查

### 6.1 虚拟环境脚本路径问题

**现象**：把校验脚本放在 `eval/` 子目录后报错 `no password supplied`

**原因**：脚本里用 `Path(__file__).resolve().parents[2]` 定位项目根目录，但 `eval/verify_data.py` 只隔了一层。

**修复**：
```python
ROOT = Path(__file__).resolve().parents[1]   # 注意是 1 不是 2
load_dotenv(ROOT / ".env")
if not os.getenv("PGPASSWORD"):
    raise SystemExit(f"[FAIL] 未读到 .env，请检查路径: {ROOT / '.env'}")
```

**教训**：加显式的失败提示，比报 `no password supplied` 更容易定位问题。

### 6.2 SQL 文件重复执行

**问题**：`schema.sql` 里用了 `CREATE TABLE`，重复执行会报"表已存在"。

**方案**：文件开头加 `DROP TABLE IF EXISTS ... CASCADE`，保证可重复执行（幂等）。

```sql
DROP VIEW  IF EXISTS v_creator_overview CASCADE;
DROP TABLE IF EXISTS party_traits CASCADE;
DROP TABLE IF EXISTS deals CASCADE;
...
```

**注意**：这种方式会**清空数据**。生产环境应改用 migration 工具（如 Alembic）。

### 6.3 PowerShell 输出中文乱码

**现象**：Python 脚本输出到 PowerShell 管道后，中文变乱码（如 `鎵ц瀹屾垚`）。

**原因**：PowerShell 默认编码与控制台不匹配。

**三种解法**：
1. 设置 `$env:PYTHONIOENCODING = "utf-8"` 后再运行
2. 输出重定向到文件用 `-Encoding utf8`，再用 `Get-Content` 读
3. **直接用 Python 读数据库验证**（最可靠）

**判断依据**：如果乱码呈现"规律性替换"（如 `鎵ц`），基本可确认是编码显示问题而非数据损坏。

## 八. 部署方案的探索与收敛（重要）

### 8.1 探索过程

**初始设想**：把 Qwen3 系列模型部署到云端 GPU，供本地代码调用。

**三次尝试**：

| 尝试 | 平台 | 结果 |
|---|---|---|
| 1 | 阿里云 PAI-DSW | ❌ 公网地址需阿里云登录态，代码访问被 302 重定向 |
| 2 | 魔搭社区 Notebook | ❌ 端口映射能力有限，实例结束服务终止 |
| 3 | 魔搭创空间（Studio） | ⚠️ 可提供免鉴权公网 HTTPS，但 GPU 需申请「xGPU乐园」，有门槛 |

### 8.2 PAI-DSW 的关键验证

**验证命令**：
```powershell
curl.exe -I "https://219876-7263-proxy-8000.dsw-gateway-cn-hangzhou.data.aliyun.com"
```

**实际返回**：
```http
HTTP/1.1 302 Found
location: https://account.aliyun.com/login/login.htm?oauth_callback=...
```

**解读**：
- 浏览器能访问 = 因为带着阿里云登录 Cookie
- `curl` 被跳转 = 没有 Cookie，说明**需要身份认证**
- 地址含 `?appId=MAAS` = 为 Model-as-a-Service 设计，默认要求阿里云认证

**结论**：**DSW 适合开发调试，不适合作为代码可调用的模型服务。**

### 8.3 魔搭创空间的关键规则（调研所得）

| 规则 | 说明 |
|---|---|
| 端口固定 **7860** | 不可修改；8080 被平台占用 |
| 只暴露**一个端口** | 多服务需容器内用 **Nginx 反向代理** |
| 文件系统**不持久** | 重启即丢；持久化需用 `/mnt/workspace` |
| Docker 部署需**实名认证** | 并绑定阿里云账号 |
| GPU 需申请 **xGPU乐园** | 审核制；免费版仅 2核CPU+16G内存 |

**社区已验证**：Docker 创空间可匿名访问自定义接口、接收 POST 回调（有实际支付项目案例）。

### 8.4 最终方案（收敛）

**放弃模型自部署，采用分层方案**：

```
本地机器                          云端
┌──────────────────────┐         ┌─────────────────┐
│ Ollama               │         │ DashScope API   │
│ └ bge-m3 (embedding) │         │ └ DeepSeek-V4-Flash     │
│                      │         │   (意图/解析/生成)│
│ PostgreSQL           │         └─────────────────┘
│ └ 结构化数据          │                  ▲
│                      │                  │
│ ChromaDB             │                  │
│ └ 向量库（持久化）    │──────────────────┘
└──────────────────────┘
```

**为什么这样分层**：

| 组件 | 本地/云端 | 理由 |
|---|---|---|
| **Embedding** | **本地** | ① 换模型会导致向量库全量重建，必须定死；② 进程内调用无网络往返 |
| **向量库** | **本地** | 必须持久化，不能放临时实例 |
| **主模型** | **云端** | 4GB 显存跑不了可用模型；**切换不影响向量库** |

**核心洞察**：**Embedding 是最不该频繁更换的一层**，因为它的输出被持久化。所以 embedding 必须一次定死并本地化；而主模型可以随时切换。

### 8.5 结论

> **环境部署不应阻塞业务逻辑开发。**

正确顺序：

```
① 本地先跑通检索链路（embedding 本地 + 主模型调 API）
② 验证效果、产出数据
③ 最后再考虑部署优化
```

本节所述的部署探索最终未产出可用方案，收敛为第 8.4 节的分层方案；期间未新增业务代码。

### 8.6 公开数据抓取可行性验证（2026-09-22）

**背景**：达人公开数据（粉丝数 / 报价）会随时间变化，需确定"自动刷新"还是"人工导出"。

**验证方式**（脚本 `eval/test_public_fetch.py`，低频单次探测，不做绕过与批量请求）：

| 目标 | 结果 |
|---|---|
| 抖音搜索页（无登录） | HTTP 200，但正文无数据（JS 空壳，真数据在需签名的异步接口） |
| 抖音 web 搜索接口 | HTTP 200，返回长度 0（签名校验拦截） |
| 小红书搜索页（无登录） | 直接返回登录页 |
| iesdouyin 旧用户接口 | 已废弃（返回 113 字节空壳） |
| 星图 / 巨量算数 | 首页即要求登录 |

**结论**：无登录态取不到达人公开数据。若要做自动化抓取，需同时解决：

1. 登录态获取与续期（Cookie 维护）；
2. 请求签名（抖音 `a_bogus` 等）；
3. 无头浏览器渲染（Playwright 等）；
4. 抗风控（频率限制、封禁）。

综合为**持续维护成本**，而该需求频率低，性价比不成立。

**决策**：公开数据刷新采用 **L1 方案**——运营从星图后台定期批量导出 → `import_data.py` upsert；数据新鲜度以 `data_updated_at` 字段 + 提示形式呈现，不做自动抓取。

> L2（浏览器自动化）/ L3（付费 API）作为远期选项保留，待需求频率上升或平台开放接口时再评估。

## 十三. 资产入库与运营成本设计（2026-09-21 补充）

### 13.1 背景与问题

本节源于一个核心设计问题：**如何把日常运营的事件闭环纳入资产库，同时把运营的数据处理成本压到最低？**

拆解为三个子问题：

1. Agent 的边界在哪（哪些是运营要操作的，哪些是系统自己干的）
2. 运营正常工作流里，经验资产从哪冒出来（闭环怎么补）
3. 运营成本怎么压到最低

**结论：完整设计另见新文档 `docs/资产入库与运营成本设计.md`**，本节只记录关键结论与对实施的影响。

### 13.2 核心矛盾与破解

**矛盾**：前台（运营日常）要快，后台（资产积累）要慢，两者节奏冲突。若设计成"运营每做一个动作都要顺手沉淀"，结果必然是运营抗拒 → 应付了事 → 系统退化成报表工具。

**破解**：切成前台/后台，并立铁律：

> **运营只干前台。后台沉淀必须是「自动触发 + 极低成本确认」，绝不能是「额外任务」。**

### 13.3 Agent 边界的最终定义

| 层 | 内容 | 谁触发 | 运营感知 |
|---|---|---|---|
| **前台（①~⑦）** | 联网聊天、资产咨询、公开数据咨询、话术构思、刊例生成、达人商单匹配、对齐问题清单 | 运营主动 | 我在用工具干活 |
| **后台（⑧）** | 数据入库管道 | **系统自动** | 几乎感觉不到 |
| **拦截（⑨）** | 人工确认 | 危险动作前自动中断 | 卡一下 |

**关键判断：⑧ 和 ⑨ 不是运营的"功能"，而是系统的"副作用"。** 运营不会主动发起"入库"，只会在完成商单时标注结案；系统据此自动启动 ⑧。

### 13.4 闭环补上的机制：状态流转触发

`deals.status` 状态机：`negotiating → signed → producing → published → settled`

**当运营把商单改成 `settled`（结案），系统自动**：
1. 收集该商单所有关联数据（结构化字段、谈判记录、对齐检查的跳过项、自由文本备注）
2. LLM 抽取结构化条目（trait / review）
3. 生成待确认列表推送给运营

**为什么不用"提交案例"按钮**：改 `status` 是运营本来就必经的动作（不结案无法对账），挂在此处成本为零；额外的独立按钮在实际使用中会被规避。（决策 D-11）

### 13.5 raw 最小形态：截图 + 3 句话总结

**这是 V1 唯一需要运营"额外提供"的东西。**

```
运营动作：
1. 贴几张截图（随手截的就行）
2. 写 3 句话总结
3. 表单选归属（提交人 / 甲方 / 达人方）
```

**关键洞察**：**运营手写的总结本身即 `source_quote`。**

因为它是人写的、人确认的，**不经过 OCR 失真**。所以：

| 做法 | `source_quote` 质量 | 结论 |
|---|---|---|
| 只存截图不 OCR | ❌ 空着 | 无法防幻觉，违反核心设计 |
| 截图 + OCR | ⚠️ 可能认错字 | 原话失真，溯源不可靠 |
| **截图 + 运营手写总结** | ✅ 人写的，忠实 | **V1 采用** |

**因此 OCR 在 V1 不是必需项**（决策 D-15）。运营懒得写总结时将来再加。

### 13.6 归属识别：由表单提供，不由系统推断

**早期设计的错误**：试图让系统从文本里猜"这段聊天属于哪个达人、哪个甲方"（原 L2 归属识别层，被判定为"最难的一层"）。

**修正**：提交案例时必然要标注「提交人/甲方/达人方」，**归属信息是人工给的，不需要系统猜**。

**管道复杂度因此从 5 层降到 3 层**：

```
❌ 原设计：L0 采集 → L1 格式归一 → L2 归属识别 → L3 抽取 → L4 确认 → L5 向量化

✅ 修正后：提交（截图+总结+表单归属）→ 抽取 → 确认 → 入库+向量化
```

**砍掉了 L0 采集层和 L2 归属识别层** —— 这两层原本最难、最依赖真实企业环境。（决策 D-13）

### 13.7 冷启动三阶段

```
阶段 A：结构化数据撑骨架（不需 LLM）→ creators / brands / deals 客观字段
阶段 B：商单表持续维护（不需 LLM）  → deals 结构化字段 + negotiation_notes
阶段 C：自由文本沉淀（需 LLM 抽取）  → party_traits / deal_reviews
```

**关键论点**：
> 冷启动不是"先把库建满再上线"，而是"**先用结构化数据上线，边用边积累私有经验**"。
> 资产的复利来自**持续使用**，不是一次性导入。

**为什么阶段 A/B 重要**：历史经验必然已丢失（微信不长期保存、复盘笔记散落），阶段 C 的数据只能从零开始。若等 C 建好才上线，项目会卡死几个月。而 A/B 的数据现在就有，且能独立提供价值。

### 13.8 允许运营什么都不交（重要）

如果结案时运营不想确认：
- 抽取结果存为 `verified = FALSE`
- **不参与检索**（防脏数据，与既有铁律一致）
- **但保留在库里**，随时可回去确认

**设计哲学：把「沉淀」从义务变成权利。义务会被逃避，权利会被使用。**（决策 D-14）

### 13.9 确认成本压缩手段

| 手段 | 效果 |
|---|---|
| 默认全选，只取消明显错的 | 从"逐条勾选"变"看一眼点确认" |
| 可疑项才高亮（`confidence` 低 / 无 `source_quote`） | 注意力只花在需要判断处 |
| 批量确认（一个商单一次提交） | 减少操作次数 |
| 移动端可确认 | 碎片时间可完成 |
| 不确认不阻塞 | 消除"必须现在做"的压力 |

**成本目标**：默认路径 10~20 秒，愿意多写则 50 秒。

### 13.10 对数据库的影响

**缺失字段**：现有 `party_traits` 只有 `source_quote`（一句原话）和 `source_deal_id`，**缺「来源渠道」和「原始文件定位」**，无法支撑完整的溯源链。

需补两个字段：

| 字段 | 类型 | 用途 |
|---|---|---|
| `source_channel` | `VARCHAR(32)` | `manual_note` / `screenshot` / `import` / `chat_export` |
| `source_ref` | `TEXT` | 截图文件路径 / 消息 ID |

补全后溯源链：

```
trait_id → source_quote（运营写的总结）→ source_ref（截图路径）→ 原始截图文件
```

⚠️ **改动影响**：需同步修改 `schema.sql`、`init_db.py` 的 INSERT、`数据录入格式.md` 的字段表；改完重跑初始化会清空现有数据（当前全是种子数据，重建无损失）。

**状态**：✅ 已完成（2026-09-21 补 `source_channel`/`source_ref`，同步 schema.sql / init_db.py / 数据录入格式.md，重跑 init_db 验证通过）

### 13.11 生产环境演进路径（V1 不实现）

| 档 | 采集方式 | 运营动作 | 前提 |
|---|---|---|---|
| 档 1（理想） | 企业微信会话内容存档 API | **零** | 公司用企微 + 开通存档 + 员工授权 |
| 档 2（现实） | 文件夹监听 | 把文件丢进目录 | 有可导出的协作渠道 |
| **档 3（V1）** | 运营提交表单 | 贴截图 + 写 3 句 | 无 |

**关键判断**：档 1 能否落地**不取决于技术，取决于目标公司用什么工具沟通**。若纯个人微信则档 1 直接不可行（个人微信不提供 API）。故 V1 不投入资源做档 1/2，作为架构能力写入设计即可。（决策 D-16）

### 13.12 一句话总结

> **运营只干前台（①~⑦），后台（⑧）系统自动干，拦截（⑨）只在危险动作前出现。**
> **运营的成本只在「结案」时多花 10~50 秒。**

## 十五. 数据质量修复与消融实验结论（2026-09-22）

### 15.1 背景：文本模板化导致评测失真

步骤③向量化后，`creators` 表 89 个达人中有 58 个（C032~C089）的文本字段使用模板化描述：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 唯一文本数 / 总数 | 48 / 89 | **89 / 89** |
| 文本唯一率 | 53.9% | **100.0%** |

**后果**：rerank 的候选文档彼此几乎无差异，CrossEncoder 无法区分——上一轮消融得出「rerank 无提升」的结论，实为该缺陷造成的**假象**。

### 15.2 数据修复

对 58 个达人的 `profile_text` / `content_style` 等文本字段改写为差异化描述。示例（母婴组）：

- 修复前：`母婴领域的头部达人，粉丝画像清晰、内容稳定，适合品牌垂类合作。`
- 修复后：`全网顶流母婴知识IP「年糕妈妈」，从新手妈妈视角分享育儿实操与辅食喂养。粉丝以0-3岁宝宝家庭为主，信任度高、复购意愿强，是母婴垂类的头部权威账号。`

同步完成 ID 前缀冲突修复（clarify 用例引用的 `C001-C003` → `Q001-Q003`）。

修复后经 `vectorize.py` 全量重建向量库（`upsert` + 固定 ID，覆盖式重建，不产生新旧并存脏数据），并逐字段比对：creators 的 356 个字段块与数据库**零不一致**；向量总数 446 = creators 356 + deals 34 + deal_reviews 18 + brands 8 + party_traits 30。

### 15.3 消融实验结论（数据修复后重跑）

评测样本：10 条 recall 用例（R001–R010），每策略独立评测。

| 策略 | Recall@1 | Recall@3 | Recall@5 | MRR | NDCG@10 |
|---|---|---|---|---|---|
| 纯 SQL 硬过滤 | 0.050 | 0.200 | 0.900 | 0.297 | 0.450 |
| 纯向量（基线） | 0.400 | 0.650 | 1.000 | 0.715 | 0.776 |
| 混合检索（无 rerank） | 0.450 | 0.700 | 1.000 | 0.715 | 0.797 |
| **混合 + Rerank** | **0.650** | **1.000** | 1.000 | **0.950** | **0.955** |

**rerank 相对 hybrid 的增量**：Recall@1 **+20.0pp**、Recall@3 **+30.0pp**、MRR **+23.5pp**、NDCG@10 **+15.8pp**。

Recall@5/@10 已饱和（均为 1.0），rerank 的价值体现于**排序质量**（Recall@1/@3、MRR、NDCG）。

> 另一条结论：纯 SQL 硬过滤的 Recall@1 仅 0.05、MRR 0.297，印证架构设计——**SQL 只负责圈定候选集，排序必须依赖向量与 rerank**。

### 15.4 结论与决策变更

| 类型 | 结论 |
|---|---|
| 实现 | rerank 实现无缺陷；数据修复后表现正确 |
| 数据 | **已修复**（唯一率 53.9% → 100%），旧结论「rerank 无提升」被推翻 |
| 决策 | **D-03 撤销**：V1 启用 Rerank，线上 `/search` 默认策略改为 `hybrid_rerank` |
| 评测标注 | R008/R010（泛化垂类查询）标注偏弱，rerank 在这两条上出现劣化（C025 第2→第4、C022 第1→第5）。此类查询经 SQL 过滤后候选全为同垂类，语义排序空间有限；后续应补充语义更细的 recall 用例 |

### 15.5 配套代码变更

| 文件 | 变更 |
|---|---|
| `src/retrieval/hybrid_search.py` | 新增 `SEARCH_STRATEGY`（默认 `hybrid_rerank`）；`build_reasons()` 按该策略检索；`hybrid_rerank` 分支补充 `rerank.is_enabled()` 判断（此前该开关失效，形同虚设） |
| `.env` / `.env.example` | `RERANK_ENABLED` 由 `false` 改为 `true`；新增 `SEARCH_STRATEGY=hybrid_rerank` |

**性能代价**：rerank 为 CPU 端 CrossEncoder 推理，每次请求约增加 2~5 秒。如需回退，将 `.env` 的 `RERANK_ENABLED` 置为 `false` 即可退化为 hybrid，无需改代码。

> **遗留限制**：本结论建立在 10 条 recall 用例上，样本量偏小，建议扩充用例后复核稳定性。
