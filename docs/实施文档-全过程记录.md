## 三. 数据库设计

### 3.1 Schema 设计要点

**文件**：`src/db/schema.sql`

**5 张表 + 1 个视图**：

| 表 | 说明 |
|---|---|
| `brands` | 甲方/品牌方 |
| `creators` | 达人档案（核心表） |
| `deals` | 商单记录 |
| `deal_reviews` | 商单复盘 |
| `party_traits` | **【核心】达人/甲方的脾气与注意事项** |
| `v_creator_overview`（视图） | 达人概览聚合 |

### 3.2 核心设计一：两类字段分离

```sql
-- 量化字段 → SQL 硬过滤
followers           INTEGER      -- 粉丝数
female_ratio        NUMERIC(4,3) -- 女性粉丝占比
quote_embed_30s     INTEGER      -- 植入30s报价

-- 文本字段 → 向量语义检索
profile_text        TEXT         -- 达人画像描述
cooperation_history TEXT         -- 历史合作情况【私有资产】
```

**为什么必须分离**：混合检索的基础。语义检索处理不了"粉丝 5-30 万"这类数值条件，必须靠 SQL。

### 3.3 核心设计二：报价双模式

**按用户确认的规则设计**：

```sql
-- 植入：按时长固定档位
quote_embed_15s     INTEGER,
quote_embed_30s     INTEGER,
quote_embed_60s     INTEGER,
-- 定制：整条报价
quote_custom        INTEGER,
-- 两种模式均可做，非二选一
coop_models         TEXT[] DEFAULT '{"placement","custom"}'
```

**约定**：不涉及直播相关字段。

### 3.4 核心设计三：party_traits（私有经验资产）

```sql
CREATE TABLE party_traits (
    trait_id        VARCHAR(16) PRIMARY KEY,
    party_type      VARCHAR(16) NOT NULL,   -- creator / brand
    party_id        VARCHAR(16) NOT NULL,
    trait_category  VARCHAR(32) NOT NULL,   -- 沟通偏好/改稿态度/排期习惯/付款要求/内容尺度
    trait_content   TEXT NOT NULL,
    severity        VARCHAR(16) DEFAULT 'info',  -- info/warning/critical
    source_deal_id  VARCHAR(16),            -- 来源商单
    source_quote    TEXT,                   -- 【防幻觉关键】原始材料原话
    confidence      NUMERIC(3,2),           -- 抽取置信度
    verified        BOOLEAN DEFAULT FALSE   -- 仅 TRUE 参与检索
);
```

**三条硬约束**：
1. `source_quote` 必须保留原文 —— 可溯源、防幻觉
2. `verified = FALSE` 的不参与检索 —— 防脏数据污染
3. 查询时只列条目原文 —— **不做二次生成**（生成会引入幻觉）

### 3.5 索引设计

```sql
CREATE INDEX idx_creators_platform    ON creators(platform);
CREATE INDEX idx_creators_followers   ON creators(followers);
CREATE INDEX idx_creators_category    ON creators(category);
CREATE INDEX idx_creators_female      ON creators(female_ratio);
CREATE INDEX idx_creators_quote_embed ON creators(quote_embed_30s);
CREATE INDEX idx_traits_verified      ON party_traits(verified);
```

**理由**：混合检索的 SQL 过滤层会频繁使用这些条件，索引保证性能。

### 4.2 刻意的设计（用于评测）

**① 边界样本（检验过滤精度）**

| ID | 昵称 | 粉丝 | 女性占比 | 植入30s | 设计意图 |

**② 报价分布（覆盖预算查询边界）**

| 垂类 | 植入30s区间 | 定制区间 | 数量 |
|---|---|---|---|

| 宠物 | 6,200 ~ 10,800 | 10,500 ~ 19,500 | 2 |
| 服饰 | 10,000 ~ 19,500 | 18,000 ~ 35,000 | 3 |
| 家居 | 4,400 ~ 8,600 | 7,200 ~ 15,000 | 2 |
| 美妆 | 2,800 ~ 20,000 | 4,800 ~ 38,000 | 5 |
| 母婴 | 4,800 ~ 26,000 | 7,500 ~ 48,000 | 2 |
| 食品 | 1,800 ~ 13,000 | 3,200 ~ 24,000 | 3 |

**③ trait 的 severity 分级**

30 条中有 **8 条 critical**，例如：
- `T003` C002：必须提前一周拿到完整brief，临期给脚本会取消
- `T006` C004：必须提供质检报告，有争议成分要求换配方

**这些是"公司私有经验"的具体体现**，也是查询时应优先展示的内容。

**④ source_quote 都保留原话**

例如 T003 的 `source_quote`：
> "不要在拍摄前一夜给新脚本，否则她会直接取消"

**不是 LLM 的总结，是原始材料的引用。** 这是防幻觉的基础。

## 六. 环境问题排查

### 6.1 虚拟环境脚本路径问题

**现象**：把校验脚本放在 `eval/` 子目录后报错 `no password supplied`

**原因**：脚本里用 `Path(__file__).resolve().parents[2]` 定位项目根目录，但 `eval/verify_data.py` 只隔了一层。

**修复**：
```python
ROOT = Path(__file__).resolve().parents[1]   # 注意是 1 不是 2
load_dotenv(ROOT / ".env")
if not os.getenv("PGPASSWORD"):
    raise SystemExit(f"[FAIL] 未读到 .env，请检查路径: {ROOT / '.env'}")
```

**教训**：加显式的失败提示，比报 `no password supplied` 更容易定位问题。

### 6.2 SQL 文件重复执行

**问题**：`schema.sql` 里用了 `CREATE TABLE`，重复执行会报"表已存在"。

**方案**：文件开头加 `DROP TABLE IF EXISTS ... CASCADE`，保证可重复执行（幂等）。

```sql
DROP VIEW  IF EXISTS v_creator_overview CASCADE;
DROP TABLE IF EXISTS party_traits CASCADE;
DROP TABLE IF EXISTS deals CASCADE;
...
```

**注意**：这种方式会**清空数据**。生产环境应改用 migration 工具（如 Alembic）。

### 6.3 PowerShell 输出中文乱码

**现象**：Python 脚本输出到 PowerShell 管道后，中文变乱码（如 `鎵ц瀹屾垚`）。

**原因**：PowerShell 默认编码与控制台不匹配。

**三种解法**：
1. 设置 `$env:PYTHONIOENCODING = "utf-8"` 后再运行
2. 输出重定向到文件用 `-Encoding utf8`，再用 `Get-Content` 读
3. **直接用 Python 读数据库验证**（最可靠）

**判断依据**：如果乱码呈现"规律性替换"（如 `鎵ц`），基本可确认是编码显示问题而非数据损坏。

## 八. 部署方案的探索与收敛（重要）

### 8.1 探索过程

**初始设想**：把 Qwen3 系列模型部署到云端 GPU，供本地代码调用。

**三次尝试**：

| 尝试 | 平台 | 结果 |
|---|---|---|
| 1 | 阿里云 PAI-DSW | ❌ 公网地址需阿里云登录态，代码访问被 302 重定向 |
| 2 | 魔搭社区 Notebook | ❌ 端口映射能力有限，实例结束服务终止 |
| 3 | 魔搭创空间（Studio） | ⚠️ 可提供免鉴权公网 HTTPS，但 GPU 需申请「xGPU乐园」，有门槛 |

### 8.2 PAI-DSW 的关键验证

**验证命令**：
```powershell
curl.exe -I "https://219876-7263-proxy-8000.dsw-gateway-cn-hangzhou.data.aliyun.com"
```

**实际返回**：
```http
HTTP/1.1 302 Found
location: https://account.aliyun.com/login/login.htm?oauth_callback=...
```

**解读**：
- 浏览器能访问 = 因为带着阿里云登录 Cookie
- `curl` 被跳转 = 没有 Cookie，说明**需要身份认证**
- 地址含 `?appId=MAAS` = 为 Model-as-a-Service 设计，默认要求阿里云认证

**结论**：**DSW 适合开发调试，不适合作为代码可调用的模型服务。**

### 8.3 魔搭创空间的关键规则（调研所得）

| 规则 | 说明 |
|---|---|
| 端口固定 **7860** | 不可修改；8080 被平台占用 |
| 只暴露**一个端口** | 多服务需容器内用 **Nginx 反向代理** |
| 文件系统**不持久** | 重启即丢；持久化需用 `/mnt/workspace` |
| Docker 部署需**实名认证** | 并绑定阿里云账号 |
| GPU 需申请 **xGPU乐园** | 审核制；免费版仅 2核CPU+16G内存 |

**社区已验证**：Docker 创空间可匿名访问自定义接口、接收 POST 回调（有实际支付项目案例）。

### 8.4 最终方案（收敛）

**放弃模型自部署，采用分层方案**：

```
本地机器                          云端
┌──────────────────────┐         ┌─────────────────┐
│ Ollama               │         │ DashScope API   │
│ └ bge-m3 (embedding) │         │ └ Qwen-Plus     │
│                      │         │   (意图/解析/生成)│
│ PostgreSQL           │         └─────────────────┘
│ └ 结构化数据          │                  ▲
│                      │                  │
│ ChromaDB             │                  │
│ └ 向量库（持久化）    │──────────────────┘
└──────────────────────┘
```

**为什么这样分层**：

| 组件 | 本地/云端 | 理由 |
|---|---|---|
| **Embedding** | **本地** | ① 换模型会导致向量库全量重建，必须定死；② 进程内调用无网络往返 |
| **向量库** | **本地** | 必须持久化，不能放临时实例 |
| **主模型** | **云端** | 4GB 显存跑不了可用模型；**切换不影响向量库** |

**核心洞察**：**Embedding 是最不该频繁更换的一层**，因为它的输出被持久化。所以 embedding 必须一次定死并本地化；而主模型可以随时切换。

### 8.5 核心教训

> **环境部署不该阻塞业务逻辑开发。**

正确顺序：
```
① 本地把检索链路跑通（embedding 本地 + 主模型调 API）
② 验证效果、跑出数据
③ 最后才考虑部署优化
```

**实际操作**：从开始探索部署到放弃，花了约 45 分钟，业务代码一行未写。如果一开始就采用分层方案，这 45 分钟本可以用于实现检索逻辑。

| **D-01** | Embedding 本地 + 主模型云端 | 全本地 / 全云端 | 4GB 显存限制；embedding 换模型需重建向量库，故本地定死 |
| **D-02** | 先测 bge-m3 再决定是否换 | 直接换 Qwen3-Embedding-0.6B | bge-m3 已下载（零成本）；Ollama 封装层可能规避 NaN bug；实测成本极低 |
| **D-03** | V1 不做 Rerank | 做 Rerank | 4GB 显存下与 embedding 争资源；先验证混合检索本身的效果 |
| **D-04** | 混合检索用「先过滤后向量」（L1-A） | 先向量后过滤 / 双路并集 | 保证结果 100% 符合硬条件；跑通后再加双路（L1-C）做对比 |
| **D-05** | party_traits 只抽取不生成 | 抽取 + 生成经验总结 | 生成会引入幻觉，且无法追溯 |
| **D-06** | 禁止输出伪精度评分（如"匹配度82%"） | 输出综合评分 | 评分是拍脑袋权重算的，经不起追问；改为每条理由绑定数据源 |
| **D-07** | 报价用双模式（植入档位/定制报价） | 单一报价字段 | 符合行业实际；两类计费逻辑不同 |
| **D-08** | 不做爬虫、不做微信协议逆向 | —— | 法律与商业风险不可控（详见 PRD 第 6 章） |
| **D-09** | V1 不做知识图谱 | 做 KG | 多跳推理仅占 1/4 查询类型；实体抽取准确率 70-85%，错误边难排查 |
| **D-10** | Dify 只做外壳，核心检索自建 | 全用 Dify | Dify 内置知识库是纯向量检索，**做不了混合检索与可溯源输出** |
