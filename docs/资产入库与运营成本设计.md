# StarForge 资产入库与运营成本设计

> **文档类型**：机制设计（回答"运营到底要做什么、资产库怎么长出来"）
> **版本**：v1.0
> **日期**：2026-09-21
> **与本文档的关系**：`数据录入格式.md` 讲的是**表字段怎么填**（数据规范）；本文档讲的是**运营怎么操作、系统怎么自动接住**（机制设计）。两者互补，不重复。

---

## 〇. 这份文档要解决什么问题

项目推进到中途时暴露了一个真实的定位困惑：

> "一开始想的是给运营快速抓取对齐的达人和甲方、完成刊例和对接，**但这个事件闭环没法完美纳入资产库**。如何最小化运营员工所需的成本（尽量少的处理数据）？"

拆开来是三个问题：

1. **Agent 的边界在哪？** —— 哪些是运营要操作的，哪些是系统自己干的？
2. **闭环怎么补上？** —— 运营的正常工作流里，经验资产从哪冒出来？
3. **运营成本怎么压到最低？** —— 运营最多愿意多花多少时间？

本文档逐一回答，并给出可实现的设计。

---

## 一. 核心矛盾：前台要快，后台要慢

### 1.1 矛盾陈述

```
运营的日常动作  →  要快：今天要结果，今天就得出来
资产库的积累    →  要慢：要记录、要抽取、要确认、要沉淀
```

**这两件事的节奏天然冲突。**

如果设计成"运营每做一个动作，都必须顺手沉淀资产"，结果一定是：

- 运营抗拒（多干活）
- 应付了事（随便勾选）
- 系统最终退化成"上面要的报表工具"，没人真用

**这是所有"知识库类系统"最常见的死法。**

### 1.2 破解方式：把系统切成前台和后台

| | **前台** | **后台** |
|---|---|---|
| 干什么 | 匹配、刊例、对齐、话术 | 沉淀、抽取、确认、入库 |
| 响应 | 秒级 | 异步，不阻塞 |
| 用户感知 | "我在用工具干活" | "我几乎感觉不到它" |
| 谁触发 | 运营主动发起 | **系统自动触发，运营被动确认** |
| 成本 | 运营的主要工作时间 | 趋近于零的确认时间 |

### 1.3 设计铁律

> **运营只干前台。后台沉淀必须是「自动触发 + 极低成本确认」，绝不能是「额外任务」。**

派生出的两条约束：

- 后台的任何环节，**都不能阻塞前台流程**。运营不确认，系统照样能出推介单。
- 后台的任何环节，**都要有默认值**。运营什么都不做时，系统应有合理行为。

## 二. Agent 边界的精确定义

### 2.1 三层结构（复用既有意图体系，按前台/后台重新归类）

```
┌─────────────────────────────────────────────────────────┐
│ 前台 · 运营主动调用 · 出结果即结束                        │
│                                                          │
│  ① 联网聊天        查公开信息                            │
│  ② 公司资产咨询    问"我们以前跟这个达人合作过吗"         │
│  ③ 公开数据咨询    问"这个达人粉丝多少"                   │
│  ④ 话术构思        生成建联话术                          │
│  ⑤ 刊例生成        出刊例                                │
│  ⑥ 达人商单匹配    甲方需求 → 推介单                      │
│  ⑦ 对齐问题清单    列出商单里还没对齐的坑                 │
└─────────────────────────────────────────────────────────┘
                          ↕ 边界线
┌─────────────────────────────────────────────────────────┐
│ 后台 · 系统自动触发 · 不占运营时间                        │
│                                                          │
│  ⑧ 数据入库管道    从商单事件自动抽取 → 生成待确认条目     │
└─────────────────────────────────────────────────────────┘
                          ↕ 边界线
┌─────────────────────────────────────────────────────────┐
│ 全局拦截 · 不产生内容 · 只卡住危险动作                    │
│                                                          │
│  ⑨ 人工确认        对外动作（发送/报价/入库）前强制中断   │
└─────────────────────────────────────────────────────────┘
```

### 2.2 关键判断

**⑧ 和 ⑨ 不是运营的"功能"，是系统的"副作用"。**

- 运营不会说"我要用入库功能"。
- 运营只会说"这个单子结了"。
- 系统在后台听到"结了"，自己启动 ⑧。

**这就是边界的本质**：运营的动作是业务语义（结案），系统的响应是工程语义（抽取入库）。两者通过**状态字段**解耦，而不是通过"让运营多点一个按钮"。

## 三. 闭环怎么补上：用「状态流转」触发，而不是「新任务」触发

### 3.1 关键洞察：运营本来就在产生数据

运营的日常工作中，下面这些动作**本来就会发生**，且**天然带着全部归属信息**：

| 运营本来就会做的事 | 天然包含的归属信息 | 系统能自动接住什么 |
|---|---|---|
| 用 ⑥ 匹配，生成推介单 | 甲方 + 达人 + 需求条件 | **候选关系**（未成交，不进资产库） |
| 用 ⑤ 生成刊例 | 达人 + 报价 | 报价变动 → 可更新 `creators` |
| 用 ⑦ 做对齐检查 | 商单 + 未对齐项 | **对齐行为本身就是经验**（见 3.2） |
| 用 ④ 写建联话术 | 达人 + 甲方 | 建联意图记录 |

**核心结论：运营不需要"额外做沉淀"，系统只需要"接住运营已经在产生的数据"。**

### 3.2 ⑦ 对齐检查是金矿（重点）

运营用 ⑦ 时，系统会列出"报价没确认、排期没确认、授权范围没确认"等未对齐项。

**运营实际确认了哪几项、忽略哪几项，本身就是最有价值的经验。**

举例：

```
商单 D003 的对齐清单（7 项）
  ✅ 报价          ← 运营确认了
  ✅ 排期          ← 运营确认了
  ❌ 独家期        ← 运营跳过了 → 后来出问题
  ✅ 素材授权范围   ← 运营确认了
  ❌ 改稿次数      ← 运营跳过了 → 后来扯皮
```

**这条"跳过"的记录，比运营事后写一百字复盘都真实。** 因为它是在决策现场产生的，没有事后归因偏差。

而这**不需要运营多做任何一件事** —— 系统本来就知道他跳过了哪几项。

### 3.3 触发机制：`deals.status` 流转

`deals` 表已有 `status` 字段，定义完整状态机：

```
negotiating → signed → producing → published → settled
                                                ↑
                                          到这里触发 ⑧
```

**当运营把商单状态改成 `settled`（结案），系统自动：**

1. 收集该商单的所有关联数据：
   - `deals` 自身的字段（报价、排期、授权范围）
   - `deals.negotiation_notes`（如有）
   - ⑦ 对齐检查留下的"跳过项"记录
   - 运营在该商单下写的任何自由文本备注
2. 调 LLM 抽取结构化条目（trait / review）
3. 生成**待确认条目列表**，推到运营面前

**运营要做的事只有一件：点开待确认列表，扫一眼，勾选，确认。**

### 3.4 为什么不直接用「商单事件」而要绕一层 `status`

有人会问：为什么不做个"提交案例"按钮，运营主动提交？

**因为那还是"额外任务"。** 而改 `status` 是运营**本来就必须做**的事（不结案，财务没法对账）。把抽取挂在这个必然发生的动作上，才是零成本。

## 四. 最小化运营成本的具体设计

### 4.1 成本目标

| 环节 | 目标耗时 |
|---|---|
| 结案 + 触发（改 status） | 0 秒额外（本来就要做） |
| 待确认列表扫一眼 | 10 ~ 20 秒 |
| "贴截图 + 写几句总结"（可选） | 30 秒 |

**总计：默认路径 10~20 秒，愿意多写则 50 秒。这是可接受的上限。**

### 4.2 raw 的最小形态：截图 + 几句话

这是本项目 **V1 唯一需要运营"额外提供"的东西**，也是整个设计的关键。

**运营动作：**

```
1. 贴几张截图（微信沟通、邮件、报价单，随手截的就行）
2. 写 3 句话总结
3. 可选的：在表单里选归属（提交人 / 甲方 / 达人方）
```

**为什么这个形态是最优解：**

| 考虑 | 说明 |
|---|---|
| **收集成本极低** | 截图是运营已经在做的事；写 3 句话成本可忽略 |
| **不需要 OCR 也能溯源** | **运营写的总结本身就是 `source_quote`** —— 它是人写的、人确认的，不经 OCR 失真 |
| **不需要复杂解析** | 不涉及聊天记录导出、格式归一、参与者识别 |
| **归属信息不靠猜** | 表单三个下拉框直接给（见 4.3） |

### 4.3 归属识别：由表单提供，不由系统推断

**早期设计的错误**：试图让系统从文本里猜"这段聊天属于哪个达人、哪个甲方"。

**修正后的设计**：提交案例时**必然要标注「提交人 / 甲方 / 达人方」**，归属信息是人工给的，不需要系统猜。

这样解析管道的复杂度大幅下降：

```
❌ 原设计（5 层）
提交 → L0 采集 → L1 格式归一 → L2 归属识别 → L3 抽取 → L4 确认 → L5 向量化

✅ 修正后（3 层）
提交（截图 + 总结 + 表单归属）
   ↓
抽取（LLM 抽 trait_category + trait_content，source_quote = 运营写的总结）
   ↓
确认（默认全选，扫一眼点确认）
   ↓
入库 + 向量化
```

**砍掉了 L0 采集层和 L2 归属识别层** —— 这两层原本是最难、最依赖真实企业环境的，现在因为"归属由表单给"而直接消失。

### 4.4 数据流图

```
运营提交
   │
   ├── 截图 ──────────────→ 存档，路径写入 source_ref
   │
   ├── 3 句话总结 ────────→ 直接作为 source_quote（不经 OCR）
   │
   └── 表单归属 ──────────→ party_type / party_id / source_deal_id
            │
            ▼
      LLM 抽取
            │
            ├─ trait_category（沟通偏好/改稿态度/...）
            ├─ trait_content （事实条目，一句话）
            └─ severity      （info/warning/critical）
            │
            ▼
      写入 party_traits（verified = FALSE）
            │
            ▼
      运营确认 → verified = TRUE
            │
            ▼
      向量化 → ChromaDB → 下次 ⑥ 匹配时用上
```

### 4.5 把确认成本继续压低的手段

| 手段 | 效果 |
|---|---|
| **默认全选，只取消明显错的** | 从"逐条勾选"变成"看一眼点确认" |
| **可疑项才高亮**（`confidence` 低、无 `source_quote`） | 运营注意力只花在真正需要判断处 |
| **批量确认**：一个商单的所有条目一次提交 | 减少操作次数 |
| **移动端可确认** | 碎片时间即可完成 |
| **不确认也不阻塞**：躺在列表里，不影响主流程 | 消除"必须现在做"的压力 |

### 4.6 反直觉但重要的设计：允许运营什么都不交

如果某次结案运营就是不想确认：

- 抽取结果存为 `verified = FALSE`
- **不参与检索**（防脏数据污染，与既有铁律一致）
- **但保留在库里**，随时可以回去确认

**为什么这样设计：**

- 运营**没有任何心理负担** —— 不确认不影响任何事，只是这条经验暂时不用
- 哪天他想起来了，点一下就能激活
- **比"必须完成"的设计留存率高得多**

> **设计哲学**：把"沉淀"从**义务**变成**权利**。义务会被逃避，权利会被使用。

## 五. 冷启动：资产库怎么从零长出来

### 5.1 冷启动的真实困难

| 困难 | 说明 |
|---|---|
| 库是空的 | RAG 检索不出任何东西，系统看起来"没用" |
| 历史经验已丢失 | 微信记录不长期保存、复盘笔记散落各处、口头传承无文档 |
| 无法考古 | 三个月前的沟通记录大概率已经找不到 |

**结论：冷启动不能靠"把历史挖出来"，只能靠"从今天起积累"。**

### 5.2 三阶段策略

```
阶段 A：结构化数据撑骨架（不需要 LLM）
   │  数据来源：公司已有的结构化数据 / 人工录入 / Excel 导入
   │  落到：creators、brands、deals 的客观字段
   │  价值：即使经验层为空，⑥ 匹配已可提供基础服务
   ▼
阶段 B：商单表持续维护（不需要 LLM）
   │  数据来源：运营在系统里改 status、填报价排期授权
   │  落到：deals 的结构化字段 + negotiation_notes
   │  价值：闭环开始产生数据
   ▼
阶段 C：自由文本沉淀（需要 LLM 抽取）
   │  数据来源：结案时"贴截图 + 写几句总结"；⑦ 对齐检查的跳过记录
   │  落到：party_traits、deal_reviews
   │  价值：私有经验资产开始复利增长
```

**关键论点：**

> 冷启动不是"先把库建满再上线"，而是"**先用结构化数据上线，边用边积累私有经验**"。
> 资产的复利来自**持续使用**，不是一次性导入。

### 5.3 阶段 A/B 为什么重要

很多人做知识库项目时，会因为"经验层最有价值"而all-in阶段C。这是错的：

- 阶段 C 的数据**必然从零开始**（历史丢失），初期库几乎是空的
- 如果等阶段 C 建好才上线，项目会卡死几个月
- 而阶段 A/B 的数据**现在就有**，且能独立提供价值

**正确顺序**：A/B 先上线提供价值 → 用起来 → C 在真实使用中长出来。

### 5.4 最小可行的 raw 来源（V1）

| 来源 | 形态 | 需不需要 LLM | 归属来源 |
|---|---|---|---|
| 结构化数据导入 | Excel / CSV / 数据库导出 | ❌ 直接映射字段 | 数据自带 |
| 商单表维护 | 运营改 status / 填字段 | ❌ 本身就是结构化输入 | 表单 |
| **自由文本沉淀** | **截图 + 3 句话总结** | ✅ 走抽取 | **表单三个下拉框** |

**注意第三条**：raw 的最小形态就是"运营随手贴的截图 + 几句话"，**不需要聊天记录导出、不需要企微对接、不需要 OCR**。

## 六. 数据库支撑

### 6.1 现有字段已覆盖的部分

| 需求 | 现有字段 | 状态 |
|---|---|---|
| 事实条目内容 | `party_traits.trait_content` | ✅ |
| 原文引用（防幻觉） | `party_traits.source_quote` | ✅ 运营写的总结填入此处 |
| 归属：哪一方 | `party_type` + `party_id` | ✅ 由表单提供 |
| 归属：哪个商单 | `source_deal_id` | ✅ 由表单提供 |
| 人工确认闸门 | `verified` | ✅ |
| 抽取置信度 | `confidence` | ✅ 用于"可疑项高亮" |
| 分级 | `severity` | ✅ |

### 6.2 缺失字段（需补）

要让溯源链完整（`trait → source_quote → 原始材料`），需要补两个字段：

| 字段 | 类型 | 用途 |
|---|---|---|
| `source_channel` | `VARCHAR(32)` | 来源渠道：`manual_note` / `screenshot` / `import` / `chat_export` |
| `source_ref` | `TEXT` | 原始材料定位：截图文件路径 / 消息 ID |

**补上后溯源链：**

```
party_traits.trait_id
   ↓
party_traits.source_quote   （运营写的那几句总结）
   ↓
party_traits.source_ref     （截图文件路径）
   ↓
原始截图文件                 （可点开核对）
```

> ⚠️ **改动影响**：`schema.sql` 需同步修改，`init_db.py` 的 INSERT 语句需同步；改完要重跑初始化，**会清空现有数据**（当前全是种子数据，重建无损失）。同时需同步更新 `数据录入格式.md` 的字段表。

### 6.3 为什么 `source_channel` 有价值

不只是一个记录字段，它能支撑一个真实的分析需求：

```
问题：我们的经验资产主要从哪来？
  manual_note  : 120 条  ← 运营主动写的
  screenshot   :  45 条  ← 结案时贴的
  chat_export  :   0 条  ← 还没接
  import       :  10 条  ← 历史导入

结论：主要靠运营主动写 → 说明"结案触发"的机制起作用了
```

## 七. 完整闭环（最终形态）

### 7.1 运营视角（能看到、要操作的）

```
甲方提需求
   ↓
⑥ 匹配 → 推介单（含可溯源理由）
   ↓
④ 生成建联话术 → ⑨ 确认 → 发出
   ↓
⑦ 对齐检查 → 列出 N 项没对齐
   ↓  （系统静默记录：运营跳过/确认了哪几项）
（谈成）改 status = signed
   ↓
（执行完）改 status = settled          ← 运营唯一天然会做的动作
   ↓
  ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄
   ↓
【系统后台自动】⑧ 收集数据 → LLM 抽取 → 生成待确认列表
   ↓
【运营】贴截图 + 写 3 句总结 → 扫一眼 → 确认     ← 成本 30~50 秒
   ↓
入库 → 向量化 → 下次 ⑥ 匹配时用上
```

### 7.2 运营视角（看不到、也不需要知道的）

```
· 格式归一 / 文本切块
· 归属映射（表单已提供，无需推断）
· 向量化（bge-m3）
· 检索合并（L1-A 先过滤后向量；后续 L1-C 双路并集）
· 可溯源理由的字段绑定
· ChromaDB 索引维护
```

### 7.3 一句话总结

> **运营只在「结案」这一个已有动作上多花 10~50 秒，其余沉淀全部自动化。**

## 八. 伪代码（结案触发 + 待确认列表）

> 用途：面试时可展示"知道怎么落地"，非可运行代码。

```python
# ============ 触发：状态流转到 settled ============

def on_deal_status_changed(deal_id: str, old: str, new: str):
    """商单状态变更钩子。运营改 status 时自动调用。"""
    if new != "settled":
        return  # 只在结案时触发

    # 1. 收集该商单的所有关联素材
    material = collect_material(deal_id)
    #   ├─ deals 结构化字段（报价/排期/授权范围）
    #   ├─ deals.negotiation_notes
    #   ├─ ⑦ 对齐检查留下的 skipped_items
    #   └─ 运营在该商单下写的自由文本备注

    # 2. LLM 抽取（只抽取，不生成）
    candidates = extract_traits_and_reviews(material)

    # 3. 落库为草稿态（verified = FALSE，不参与检索）
    for c in candidates:
        c.verified = False
        c.confidence = c.confidence or 0.0
        save_draft(c)

    # 4. 生成待确认列表，推送给运营
    notify_review_queue(deal_id, candidates)
    # 注意：不阻塞。运营不看也不影响任何事。


# ============ 抽取：强制 source_quote ============

EXTRACT_PROMPT = """
从以下材料中抽取「达人/甲方的脾气、注意事项」。

硬约束：
1. 每条必须是材料中的【事实】，禁止推断、禁止总结、禁止编造。
2. 每条必须附 source_quote —— 从材料中原样摘出的一句话。
   如果找不到可引用的原话，【不要输出这条】。
3. 输出 JSON 数组，字段：
   trait_category, trait_content, severity, source_quote, confidence
"""

def extract_traits_and_reviews(material: dict) -> list:
    resp = llm.chat(EXTRACT_PROMPT, material_to_text(material))
    items = parse_json(resp)

    # 过滤：没有 source_quote 的一律丢弃（防幻觉闸门）
    return [i for i in items if i.get("source_quote")]


# ============ 确认：默认全选，可疑项高亮 ============

def build_review_queue(deal_id: str) -> list:
    """构建待确认列表。"""
    drafts = load_drafts(deal_id)
    for d in drafts:
        # 默认全选
        d.checked = True
        # 可疑项标记（low confidence 或无 quote）
        d.suspicious = (d.confidence < 0.75) or (not d.source_quote)
    return drafts


def on_operator_confirm(deal_id: str, item_ids: list):
    """运营点了确认。"""
    for tid in item_ids:
        trait = load_trait(tid)
        trait.verified = True          # 闸门打开
        save_trait(trait)
        embed_and_index(trait)         # 向量化入 ChromaDB
```

### 8.1 三个设计点

| 点 | 说明 |
|---|---|
| **不阻塞** | `on_deal_status_changed` 里没有等待用户输入，是异步推进的 |
| **闸门前置** | 抽取阶段就过滤掉无 `source_quote` 的条目，不给脏数据进库机会 |
| **默认全选** | 降低确认成本的关键，从"逐条决策"变成"扫一眼" |

## 九. 生产环境演进路径（V1 不实现，仅作架构展示）

V1 走"运营贴截图 + 写总结"。将来若要进一步降低运营成本，可演进为**无感采集**：

| 档 | 采集方式 | 归属识别 | 运营动作 | 前提条件 |
|---|---|---|---|---|
| **档 1（理想）** | 企业微信会话内容存档 API | 外部联系人 ID 自动映射 | **零** | 公司用企微沟通 + 开通会话存档 + 员工授权 |
| **档 2（现实）** | 文件夹监听（文件丢进指定目录） | 参与者识别 + 下拉兜底 | 把文件扔进文件夹 | 公司有飞书/钉钉/邮件等可导出渠道 |
| **档 3（V1 采用）** | 运营提交表单 | 表单三个下拉框 | 贴截图 + 写 3 句 | 无 |

### 9.1 明确排除的方案

| 方案 | 排除理由 |
|---|---|
| 平台爬虫（巨量星图/花火） | 违反平台协议与《反不正当竞争法》，工程与商业风险不可控 |
| 个人微信协议逆向 | 封号风险极高，违反用户协议 |
| 强制员工导出聊天记录 | 员工没有动机、执行不规范、事后补不了，做成流程必然烂尾 |

### 9.2 演进的关键判断

**档 1 能不能落地，不取决于技术，取决于目标公司用什么工具沟通。**

如果对方就是纯个人微信，档 1 直接不可行（个人微信不提供 API）。所以 V1 不投入资源做档 1/档 2，等确认了目标公司的真实协作环境再决定。

## 十. V1 边界声明

| 项 | V1 做不做 | 说明 |
|---|---|---|
| 结构化数据导入 | ✅ 做 | 阶段 A/B 的基础 |
| 结案状态触发抽取 ⑧ | ✅ 做 | 核心机制 |
| 待确认列表 + 极低成本确认 | ✅ 做 | 核心机制 |
| 截图 + 总结 → trait 抽取 | ✅ 做 | 核心链路 |
| OCR（从截图提取文字） | ❌ 不做 | 运营写的总结已作为 `source_quote`，无需 OCR。将来运营懒得写总结时再加 |
| 企微会话存档对接 | ❌ 不做 | 需要真实企业环境才能验证，简历作品无此条件 |
| 文件夹监听 | ❌ 不做 | 同上 |
| 对齐检查的静默记录 | ⚠️ 依赖 ⑦ | ⑦ 是 V2 功能；V1 先在 `deals.negotiation_notes` 里体现 |

**Agent 边界一句话总结：**

> 运营只干前台（①~⑦），后台（⑧）系统自动干，拦截（⑨）只在危险动作前出现。
> **运营的成本只在「结案」时多花 10~50 秒。**

## 附录：设计决策记录

| 编号 | 决策 | 备选 | 理由 |
|---|---|---|---|
| **D-11** | 后台沉淀用「状态流转」触发，不用「提交按钮」 | 加"提交案例"按钮 | 改 status 是运营本来必须做的事，挂在此处是零成本；额外按钮必然被逃避 |
| **D-12** | raw 最小形态 = 截图 + 3 句话总结 | 聊天记录导出 / 企微对接 | 收集成本极低；总结本身即 `source_quote`，免 OCR 也免格式归一 |
| **D-13** | 归属信息由表单提供，不由系统推断 | 系统从文本识别参与者 | 提交时必然要标注，人工给的归属比推断可靠；L2 层因此可直接砍掉 |
| **D-14** | 允许运营不确认（`verified=FALSE` 留着） | 强制确认 | 把沉淀从义务变权利，显著提高留存率；脏数据因不参与检索而无害 |
| **D-15** | V1 不做 OCR | 做 OCR | 运营写的总结已满足溯源需求；OCR 会引入识别误差，反而损害 `source_quote` 的忠实性 |
| **D-16** | V1 不接企微/飞书 | 接 | 需真实企业环境才能验证，简历作品不具备条件；作为架构能力写入设计即可 |
